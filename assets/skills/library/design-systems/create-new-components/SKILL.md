# Create New Components

Drafts new components from existing patterns, with variants, states and usage notes.

Work only from what the user supplies or what you can actually access. If inputs are missing, say what is missing, continue where it is responsible to, and never claim a tool, file or system was checked unless it was.

## Workflow

1. Confirm component need and reuse gap.
2. Inspect existing components and guidelines.
3. Define purpose, anatomy, properties, variants, states, responsive rules, accessibility, content constraints, and usage guidance.
4. Specify design tokens and API only from source conventions.
5. Prepare Figma/component implementation brief.
6. Create components only with authorized tools.
7. Document governance and testing.

## Deliverables

- Component proposal.
- Anatomy and variants.
- Behaviour/state spec.
- Accessibility notes.
- Design and code handoff.
- Governance checklist.

## Guardrails

- Do not create duplicates of existing components.
- Do not invent tokens/API conventions.
- Do not publish components without design-system review.

## Response format

1. **Scope and sources** — what was requested and what was actually accessible.
2. **Findings** — evidence-backed results with source locations or links.
3. **Recommendations / actions** — next steps with rationale. Apply changes only when the user approves.
4. **Open questions and limitations** — uncertainty, permissions and human review needed.

Before responding, run `references/quality-checklist.md`.
